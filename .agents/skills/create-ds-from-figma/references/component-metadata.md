# Formato de la ficha del componente

`npm run finalize:import -- ROOT METADATA --diagnose [--port PORT]` examina una implementación existente sin publicar evidencia ni registrar revisiones. diagnosis contiene mode=diagnostic, execution, diagnostics.cases (comparaciones fidelity/behavior existentes, mediciones y diagnósticos AABB), diagnostics.resources, diagnostics.warnings y manifest.cases vacío. Cuerpos, recibos, capturas y caché viven en un temporal nuevo; no se admite directorio de salida suministrado por el consumidor en este modo. No cambia el formato de metadata ni de sus snapshots. Fuentes e imágenes pendientes no bloquean la recogida diagnóstica, pero conservan sus carencias y no habilitan confirmed. Los errores estáticos siguen impidiendo ejecutar código. FAIL indica fallos/bloqueos; una ejecución numéricamente limpia queda NOT VERIFIED, siempre complete=false y CLI exit 1. El diagnóstico no ejecuta el gate de entrega ni acredita fidelidad. nextActions separa autorización de recursos y REVIEW_RENDERED_DIFFERENCES por caso/check. Recursos ausentes pueden afectar geometría; la salida no atribuye automáticamente una causa. No combines --diagnose con --collect/--reviews/--check. El puerto opcional sigue las mismas reglas de recogida, y diagnosis.preview conserva el efectivo.

La recogida integrada solicita un puerto libre por defecto; `--collect --port 5189` selecciona uno explícito (0 solicita asignación automática). La salida integrada conserva collection.preview con requestedPort, port, cases y diagnosticsUrl; el result.json del adaptador conserva ese mismo objeto en preview. El puerto efectivo identifica las URL recogidas, no un servidor que siga abierto después de terminar el adaptador. Un puerto explícito ocupado falla, sin usar el servidor ajeno. --port no aplica al registro de revisiones ni al gate de solo lectura.

La finalización rechaza usage.md como archivo examinado antes de persistir informes o cambiar correspondencias, tanto si figura en verification.inputs como en inputs adicionales del revisor o en dependencias examinadas de los casos. Es una dependencia circular: escribirlo caducaría la propia confirmación. Los diagnósticos de tamaño AABB usan AABB_SIZE_DIAGNOSTIC_THRESHOLD, independiente de las tolerancias de posición/fidelidad; no convierten geometrías no comparables en FAIL objetivos.

La finalización integrada usa `npm run finalize:import -- ROOT METADATA --collect`, después una revisión explícita de los artefactos y `npm run finalize:import -- ROOT METADATA --reviews REVIEW_FILE`. REVIEW_FILE tiene schemaVersion 1 y cases [{caseId, review}], una por caso fidelity; review usa el contrato vigente del comando report. Deriva/persiste informes y hashes, revalida y actualiza atómicamente solo el JSON de correspondencias de usage.md. No genera el juicio visual ni cambia metadata. `--check` solo ejecuta el gate. Los avisos de CSS y las diferencias informativas de tamaño AABB no comparable no cambian los estados objetivos del comparador.

Las importaciones guardan `evidence: { snapshot, hash, decisions, textDimensions, translations, dispositions }`. snapshot es la ruta relativa y hash el SHA-256 devuelto por el colector. Cada binding/literal incluye observation, ID de la observación bruta. Clasificaciones y notBuilt requieren `{ target, rule, reason, observations }`, con target único y existente. Una referencia localiza, no justifica: razones manuales generan justificación NOT VERIFIED; candidatos automáticos no confirman API ni correspondencia renderizada.

`verify-figma-evidence.mjs` contrasta hechos contra la misma captura. translations explica traducciones compuestas; dispositions explica exclusión, aplazamiento o reutilización, sin rescatar omisiones esenciales. Para delegación mapped por instancia usa `{ kind: "delegated", instance, resolvedComponent, configuration, reason }`: identidad y componentProperties deben coincidir; solo contabiliza descendientes y advierte de overrides no verificados. Toda ficha mapeada exige evidence, sin excepciones. El snapshot no sustituye inventario de tokens ni comparación visual, y su hash no identifica revisión. Para approximate, figmaValue conserva el dato de observation, incluido campo y fuente PLUGIN, sin redondearlo.

Consulta este formato durante el análisis de variantes y antes de escribir `metadata.json` y el TSX. Las condiciones para importar, detenerse o actualizar están en `../SKILL.md`.

## Diagnóstico Y Registro De Recursos

`node .agents/skills/create-ds-from-figma/scripts/verification-plan.mjs requirements SNAPSHOT` deriva los requisitos existentes y añade resources/nextActions. Antes de la ficha, agrupa fuentes por ID observado e imágenes por imageHash, con observaciones, nodos y variantes; essentiality permanece UNCLASSIFIED y los casos/descriptores CSS PENDING. No deriva pesos CSS ni declara esenciales todos los recursos capturados. Se puede consultar el snapshot temporal fuera del proyecto, antes de escribir.

`node .agents/skills/create-ds-from-figma/scripts/verification-resources.mjs inspect ROOT METADATA` valida el snapshot enlazado y consulta los registros de una ficha en preparación. Requiere arrays fonts/assets/cases existentes, con casos que identifiquen variantes capturadas, no TSX ni un DS completo. Reutiliza la derivación y las reglas de carencias esenciales del gate. registration comprueba existencia/hash de los archivos; configuration puede ser DECLARED o NOT VERIFIED y loading permanece NOT RUN. Los casos declarados son subárboles afectados, no prueba de uso o visibilidad. Una ficha en preparación no se considera válida o entregada por pasar esta consulta.

Para configuration se inspeccionan verification.stylesheets, sus imports CSS incondicionales y los imports/reexports estáticos desde metadata.code.path, con ciclos acotados. El analizador compartido usa runtimeOnly y stylesheetDiscovery: excluye tipos, imports dinámicos, globs y cualquier consulta con ? (también worker/sharedworker o parámetros desconocidos); la misma política rige @import CSS. No confunde un archivo CSS auditado o una URL con una hoja cargada. CSS de paquetes instalados puede resolverse por subpath/exports sin ejecutar código, siempre dentro del proyecto; exports no resolubles y efectos secundarios de paquetes JavaScript requieren revisión. Un @font-face enlaza solo si contiene una URL local al archivo registrado y familia/estilo/peso coincidentes; se admiten pesos numéricos y rangos. Se registran stylesheet/line, sin interpretar condiciones CSS. DECLARED no demuestra selección entre src alternativos, validez CSS completa, carga, glifos, licencia o identidad. Formas no soportadas quedan NOT VERIFIED con configurationWarnings. REVIEW_FONT_CONFIGURATION pide revisar las pendientes con archivo registrado. El gate expone fontConfiguration como diagnóstico, sin endurecer su política. El cambio del analizador compartido exige nueva versión/huella del comparador y caduca confirmaciones anteriores. Recursos esenciales sin resolver y caras esenciales no cargadas siguen bloqueando; los avisos solo permiten diagnóstico provisional. Las regresiones reales comprueban hojas ausentes, imports CSS rotos y fuentes no decodificables sin permitir un cierre completo.

El resolvedor común usa la dependencia fijada resolve.exports con unsafe y condiciones explícitas, nunca createRequire. Solo acredita un destino único estable: import activo y combinaciones opcionales de browser/module y modo sin fijar/development/production; en @import añade style opcional. No impone que esas condiciones sean universales: si cambian el destino, falta una rama o hay alternativas distintas, requiere revisión del resolvedor del proyecto. Respeta orden de claves, subpaths exactos, comodines y null; no evita exclusiones buscando archivos directamente. Condiciones desconocidas, metadatos browser de remapeo, destinos no CSS/ilegibles y symlinks externos quedan sin acreditar. Sin exports, admite un subpath CSS explícito o una raíz style/main única; no inventa un índice ni ejecuta entradas JS. Esta política limitada no equivale a cargar plugins/aliases arbitrarios. Las consultas en la URL del archivo de fuente no son imports y no se usan como evidencia de su selección/carga.

Para un archivo existente autorizado y relativo al proyecto, usa `node .agents/skills/create-ds-from-figma/scripts/verification-resources.mjs register ROOT METADATA font FONT_ID SOURCE_PATH` o `node .agents/skills/create-ds-from-figma/scripts/verification-resources.mjs register ROOT METADATA image IMAGE_HASH SOURCE_PATH`. Solo cambia source de una entrada de fuente existente o de todas las apariciones capturadas de la imagen en esa ficha. Calcula SHA-256; exige cobertura sin duplicados y rechaza desconocidos, rutas externas y conflictos sin modificar metadata. Una sustitución de ruta o hash exige --replace explícito, no autorización automática. Repetir el mismo registro conserva los bytes de la ficha. La escritura es atómica y comprueba que metadata, snapshot y recurso no hayan cambiado durante la operación; puede caducar confirmaciones existentes. No modifica stylesheets ni genera @font-face, instala paquetes o copia archivos. No certifica licencia, familia, peso ni glifos: registrar el archivo equivocado no lo convierte en correcto.

nextActions usa códigos estables, resources, prerequisites, permissions, command y requiredArguments. command es null para tareas sin comando seguro, o {executable,args}; los argumentos pendientes son tipados, no marcadores interpolados en shell. Las carencias comparten AUTHORIZE_FONT_SOURCE / AUTHORIZE_IMAGE_SOURCE con el gate y la finalización; sin imageHash legible se requiere RECAPTURE_IMAGE_IDENTITY. RECHECK_REGISTERED_SOURCES pide revisar bytes inválidos, nunca sustituirlos automáticamente. Estas acciones no conceden permisos ni producen PASS visual. Este flujo usa el formato actual de source, sin catálogo, campos nuevos de metadata ni cambios del colector.

Las nextActions por ficha incluyen targets, un array de rutas de metadata relativas al proyecto. Gate y finalización usan la misma deduplicación canónica: excluyen targets al comparar acciones idénticas y unen sus destinatarios sin mutar las entradas; recursos y comandos distintos se conservan separados. Acciones globales sin ficha pueden omitir targets. Los avisos detallados de fontConfiguration se copian también a warnings del gate con prefijo de componente; no cambian su severidad.

## Comparación Renderizada General

La tolerancia TEXT de 1 px es provisional: el check geometry:PARTE incluye typographyTolerance con status provisional y requiresRenderedReview true. Aunque su resultado numérico sea PASS, measured/confirmed exige un checkReviews específico con el mismo formato y artefactos retenidos del caso que las revisiones NOT COMPARABLE de fidelidad. Documenta la comparación renderizada real de ese texto. No cambia PASS/FAIL ni permite rescatar FAIL/NOT RUN; la revisión general no lo sustituye. La versión del comparador hace caducar confirmaciones anteriores a esta obligación. El corpus real de 56 combinaciones de Inter comprueba carga/repetibilidad en dos contextos del mismo Chromium; sin ground truth equivalente de Figma no determina tolerancia entre fuentes, plataformas o renderers.

Toda ficha declara `verification.geometryPolicy: "mapped-layout-v1"`. No depende del nombre del componente ni impone Flexbox, Grid o una técnica de dibujo. La captura v2 guarda absoluteBoundingBox y absoluteTransform; el sobre del snapshot sigue en versión 1. Sin retrocompatibilidad: las capturas anteriores deben repetirse, nunca rellenarse con datos inventados.

Las mediciones usan schemaVersion 2, producer verification-preview-v2 y measurementVersion con el valor vigente de MEASUREMENT_VERSION, definido en `.agents/checks/lib/measurement-version.mjs`. Lo escribe el productor: no lo transcribas ni cambies versiones de recibos históricos. El recibo original conserva la misma measurementVersion. No son versiones del snapshot ni de la aplicación. Cada elemento conserva rect/computed y `geometry: { visible, laidOut, axisAligned, affine2d }`: visibilidad efectiva (incluidos ancestros), participación en layout y ausencia de transformaciones no soportadas. Una parte oculta puede existir en el DOM. Las caras declaradas loaded son un requisito de recurso, no prueba de la fuente de los glifos.

`node .agents/skills/create-ds-from-figma/scripts/verification-plan.mjs compare . METADATA CASE BODY [BASELINE_BODY]` compara un cuerpo con SU snapshot/configuración. Es diagnóstico, no publicación ni confirmación: verifica identidad del caso, no autenticidad ni hashes del recibo original. Emite checks con ID estable, motivo, expected/measured/delta cuando procede y summary. FAIL termina con código 1. Estados:

- PASS: comparada y dentro de tolerancia, o ausencia visual comprobada para contenido oculto.
- FAIL: diferencia detectada, contenido distinto, parte visible ausente o fuente esencial pendiente/no cargada.
- NOT COMPARABLE: equivalencia no establecida con los datos y reglas disponibles, con motivo.
- NOT RUN: no hay medición o falta el registro necesario.

En fidelity cada parte necesita una ref de nodo y un elemento DOM inequívocos para la variante. Los bounds se comparan relativos a la raíz; tolerancia fija de 1 píxel CSS por x/y/width/height, independiente de la exportación PNG y no elegida por el revisor. Solo se admiten matrices absolutas de traslación y cajas sin trazo o con trazo INSIDE en nodos admitidos. Un trazo inspeccionado pero ilegible (mixed, unavailable, mal formado, o una lectura fallida que el colector registra en coverage.issues) es desconocido, no ausente; solo un campo que el nodo no expone (`notApplicable`) significa que no hay trazo, y un texto capturado ilegible no se declara diferencia de texto: la geometría queda NOT COMPARABLE, igual que la posición parcial, hasta una revisión específica. El borde CSS no se resta automáticamente: debe conservar la caja exterior Figma INSIDE. Rotación, escala, reflejo, skew, matrices singulares/no leídas, grupos, booleanos, vectores, bounds ausentes y modos distintos de la captura quedan NOT COMPARABLE. No se invierte un AABB para reconstruir una forma ni se impone una propiedad CSS concreta.

La visibilidad se evalúa en el subárbol de la variante: contenido oculto por sí mismo o por ancestros no debe mostrarse, pero no se exige eliminarlo del DOM. Visibilidad ilegible no se presume. Las cajas exactas no se heredan por los casos behavior; sus expectativas se comprueban solo mediante invariantes explícitas: contained, anchored, centered e intrinsic-size con relación declarada.

Las fuentes esenciales de un caso de fidelidad se derivan del texto visible y no vacío de esa configuración, porque renderiza exactamente el contenido capturado. Un caso de comportamiento aporta su propio contenido y props, que pueden rellenar un texto vacío o mostrar uno oculto, pero solo donde el diseño lo permite: exige la fuente de un texto visible y no vacío, de uno cuyo contenido aporta el propio caso, de uno oculto con una propiedad de visibilidad (`componentPropertyReferences.visible`, también en sus ancestros ocultos) y de uno vacío con una propiedad de texto (`componentPropertyReferences.characters`). Una capa oculta de forma permanente (sin propiedad de visibilidad, o con opacidad 0) o un texto vacío sin propiedad de texto nunca se renderizan y no la exigen. Si las referencias no son legibles, se exige por precaución. El contexto global de modos es el modo resuelto de la raíz examinada (un `resolvedVariableModes` legible que omite la colección significa su modo predeterminado; uno ilegible no se sustituye por el predeterminado: se usa el modo explícito conocido de la raíz o el contexto queda NOT COMPARABLE, y sin contexto no se registran `localModes`): un descendiente con un modo forzado propio forma parte del diseño y se mide tal como se renderiza, sin volver incomparable el resto de partes. Esos modos locales se registran como `localModes` junto a la comprobación de geometría, como hecho de origen; nada comprueba que el código acote ese modo en ese subárbol. confirmed exige source file con bytes vigentes y una cara loaded con familia/peso/estilo correspondientes. source unresolved bloquea la confirmación, no la recogida/publicación diagnóstica. Ni el recurso loaded ni document.fonts.check demuestran cobertura de caracteres o la fuente de cada glifo.

Los informes v4 guardan `renderChecks` derivado (policy/comparatorVersion/checks/summary/scope) y `checkReviews`. Cada NOT COMPARABLE de fidelidad y cada PASS geométrico TEXT con tolerancia provisional requieren una revisión específica `{ checkId, result: "PASS", reason, artifacts: [ruta] }` con artefactos tipados del mismo informe, además del juicio visual general. La revisión alternativa no cambia el resultado numérico ni rescata FAIL/NOT RUN. El gate recalcula los hechos de confirmaciones vigentes: IDs, estados, medidas, diferencias, tolerancias y parámetros, excluyendo reason/scope. Cambiar prosa no invalida; cambiar comparatorVersion caduca la confirmación sin convertirla en corrupción. Cambios de reglas o tolerancias exigen incrementar la versión. Bajo la misma versión, una diferencia factual sigue siendo error. Las caducadas conservan el tratamiento histórico NOT VERIFIED sin editar usage.md. El test comparator-version fija dos huellas independientes: la del comparador sigue las declaraciones nombradas usadas por compareRendered/renderResultFacts/assertConfirmationChecks y sus dependencias locales, incluidas renderRequirements, textDimensionRequirements y canonicalJson; la del productor sigue previewModule/receiptHandler y renderedExpectation. No hashea validadores ajenos solo por compartir archivo. Sigue helpers/imports estáticos nuevos y rechaza formas locales no soportadas (por ejemplo imports dinámicos) en vez de omitirlas. La normalización del comparador excluye comentarios, reason/scope y diagnósticos reconocidos; la plantilla serializada del navegador se protege conservadoramente como parte del productor. No cubre implementaciones de Node/React/navegador ni toda semántica dinámica de JavaScript. Un cambio lógico exige incrementar la versión y añadir su huella revisada; no reemplazar una entrada previa. No sustituye las pruebas de resultados ni protege contra manipulación del propio test.

verify-ds imprime VISUAL por componente: confirmados, pendientes, registros fallidos, no establecidos y recuentos automáticos de confirmaciones vigentes. Un registro fallido no demuestra una diferencia visual; una fila candidate sin informe no se inventa como FAIL. El informe final debe separar PASS estático y cobertura visual, enumerando los NOT COMPARABLE/NOT RUN conocidos. El alcance es geometría mapeada y carga de fuentes, no fidelidad completa.

### Posición Parcial Y Comportamiento

El comparador declara su `comparatorVersion` (la constante `COMPARATOR_VERSION` de `render-comparison.mjs`, que no se repite aquí para no desfasarse). La política mapped-layout-v1 sigue siendo el contrato general, no un selector para saltarse reglas. Nuevas capacidades se incorporan con condiciones y versión; no por nombre de componente. Un informe sin versión no satisface este contrato.

geometry:PARTE conserva la comprobación completa. Para un vector o parte transformada se añade position:PARTE cuando la raíz es de traslación pura, ambas cajas están disponibles, la matriz Figma es 2D no singular y la medición acredita affine2d. Se compara el centro de cada AABB relativo al origen de la raíz con 1 píxel CSS por eje, sin ampliar la tolerancia para esconder diferencias. Las dimensiones se guardan como informativas: PASS de posición no confirma tamaño ni forma. Grupos/booleanos, trazos que alteran las cajas, perspectiva/3D, matrices ilegibles o raíz transformada no habilitan esta regla. Una revisión de geometry no rescata un FAIL de position.

Las invariantes behavior se declaran en expectations, con part y reason explícitos; el validador rechaza nombres/participantes/parámetros inválidos. No se deducen del nombre de la capa ni se activan solo porque cambió un texto:

- `{ kind: "contained", part, container, inset: 0, reason }`: distancias a los cuatro bordes de la caja del contenedor mayores o iguales al inset menos tolerancia. inset es un mínimo explícito en píxeles CSS, no padding inferido. part y container deben ser distintos y estar mapeados en la variante.
- `{ kind: "anchored", part, container, edge: "right", reason }`: distancia con signo al borde indicado igual a la medida en el caso baseline. edge admite left/right/top/bottom; una distancia negativa puede representar contenido exterior.
- `{ kind: "centered", part, container, axis: "x", relation: "center", reason }`: centros coincidentes en x/y dentro de tolerancia. relation preserve-offset conserva el desfase con signo medido en baseline, que no equivale a centrado. Ambas relaciones exigen eje y motivo explícitos.
- `{ kind: "intrinsic-size", observation, part, axis: "width", relation: "grow", reason }`: compara la dimensión medida con baseline usando grow/shrink/equal/change. axis admite width/height; relation y reason no se inventan a partir de auto-resize. Sin relación declarada conserva NOT COMPARABLE: cambiar contenido no garantiza cambiar cada dimensión.

anchored, centered con preserve-offset y las relaciones dimensionales requieren BASELINE_BODY del caso fidelity indicado por baseline, con mismo snapshot/ref/modos/viewport/entorno/estados. La CLI valida ambos sobres y el plan. Sin esa medición dan NOT RUN; contención puede evaluarse con la medición actual. DOM con texto distinto del content declarado da FAIL. Se requiere un elemento inequívoco por parte. centered admite el centro AABB de una parte affine2d aunque esté rotada, con raíz y contenedor sin transformaciones incompatibles; no comprueba forma. Las demás invariantes siguen exigiendo cajas axisAligned. compare sigue siendo diagnóstico, pero report deriva y persiste estos checks: todos los casos behavior asociados por baseline son obligatorios para confirmed y todos sus checks deben ser PASS, sin rescate manual de FAIL/NOT RUN/NOT COMPARABLE. No confirman variantes nuevas de Figma. La falta de comparabilidad o de ejecución de una obligación mantiene candidate/NOT VERIFIED: no demuestra un defecto visual. Un registro que ya afirme confirmed sin cumplir esas obligaciones es inválido, no una prueba de que el diseño sea incorrecto.

## Dimensiones De Texto

`evidence.textDimensions` es obligatorio, también como `[]` cuando no hay dimensiones de texto capturadas. Cada observación bruta `width` o `height` de un nodo `TEXT` necesita exactamente un registro `{ observation, behavior, rule, observations, treatment }`. `observation` identifica esa dimensión; `observations` contiene exactamente las refs de apoyo que devuelve `figma-capture.mjs dimensions SNAPSHOT`. Este registro no crea una parte ni convierte una medida en una declaración CSS.

La regla `text-auto-resize-v1` se aplica por dimensión y solo en la configuración capturada:

| textAutoResize | width | height |
| --- | --- | --- |
| WIDTH_AND_HEIGHT | content | content |
| HEIGHT | fixed | content |
| NONE o TRUNCATE | fixed | fixed |

Si el valor dimensional no es numérico, falta un auto-resize admitido, la dimensión declara `layoutSizingHorizontal/Vertical: FILL` o un sizing no admitido (distinto de FIXED/HUG), o un binding dimensional interfiere con una dimensión dependiente del contenido, el resultado es `unknown`. No se deduce centrado del nodo a partir de `textAlignHorizontal`, ni una regla de layout a partir de coordenadas. El perfil actual no captura constraints; esta regla no resuelve esa relación ni todos los límites de tamaño posibles.

`behavior` debe coincidir con el resultado del script (`fixed | content | unknown`); no es una elección libre del agente. `fixed` no significa que todos los modos tengan el mismo valor. `treatment` es una decisión distinta:

- `declaration`: solo para `fixed`; añade `cssSelector` y `cssProperty` (`width`/`inline-size` o `height`/`block-size`). Debe existir un binding o literal de la misma dimensión, nodo y destino CSS.
- `translation`: añade el mismo destino CSS y enlaza una entrada de `evidence.translations` que incluya tanto la dimensión como todas sus observaciones de apoyo, y un motivo real. Sirve para sizing intrínseco o una traducción de dimensiones fijas. La existencia de esa explicación no demuestra el comportamiento del CSS.
- `delegation`: añade `instance`, ref de una instancia `mapped` con una disposition válida. La dimensión debe pertenecer a un descendiente de esa instancia; no se delega su propia geometría por ese mecanismo.
- `unresolved`: solo para `unknown`; requiere una entrada no bloqueante en `unresolved` con `field: "textDimensions.<observation>"`, motivo y fuente reales. Si la incertidumbre impide implementar fielmente la configuración o decidir la API, comunica DS_GAP antes de registrar la importación, en lugar de usar este tratamiento.

No hay exclusión automática para texto oculto, ni tratamientos `excluded`/`notApplicable` para dimensiones que sí fueron capturadas. Un literal sobre una dimensión `content` es error aunque coincida exactamente con el tamaño de la letra de ejemplo o se marque `approximate`. Mantén ese número en el snapshot; implementa su comportamiento intrínseco mediante una traducción y compruébalo renderizado.

Ejemplo de registro para una anchura intrínseca, no evidencia para copiar:

```json
{
  "observation": "1:3#width#property",
  "behavior": "content",
  "rule": "text-auto-resize-v1",
  "observations": ["1:3#textAutoResize#property"],
  "treatment": "translation",
  "cssSelector": ".initial",
  "cssProperty": "width"
}
```

El verificador comprueba cobertura, semántica capturada y enlaces del tratamiento, no que la traducción esté realmente implementada ni que cambie correctamente al variar el contenido. `review.textDimensions` conserva esas comprobaciones pendientes. No uses solo la coincidencia de medidas para declarar fidelidad de todos los contenidos. La primera regla cubre únicamente dimensiones de texto; no impone todavía cobertura de toda la tipografía, assets o geometría de otros nodos.

## Resto De La Ficha

En una ficha importada, guarda `variants` como objeto eje → lista de valores observados (por ejemplo `{ "Size": ["Small", "Large"] }`); `states` y `tokens` son listas. Guarda en `figmaCoverage.variants` las claves de variantes observadas, iguales a las de `figma-code-map.json`; el validador compara también ejes y valores de `variants` con el mapa. Para un componente sin set ni variantes, ambos objetos de variantes son `{}` y `figmaCoverage.variants` es `[]`: no inventes una variante Figma. Esa igualdad entre archivos no puede probar por sí sola que Figma no contenía otras variantes. `unresolved` contiene solo preguntas abiertas no bloqueantes: `{ "field": "variants.Size", "reason": "...", "source": "herramienta y ref intentados", "blocking": false }`. `notApplicable` contiene conclusiones justificadas: `{ "field": "...", "reason": "...", "source": "herramienta y ref" }`. No uses `null` para sustituir objetos o listas. Los bloqueos van en el diagnóstico, no en una ficha registrada; si una ficha existente declara `blocking: true`, el validador debe fallar.

Antes del TSX, clasifica cada **valor** de cada eje Figma en `variantClassification`: `{ "Size": { "Large": { "kind": "prop", "codeProp": "size" } }, "State": { "Hover": { "kind": "interaction", "state": "hover" } } }`. Usa `kind: prop | state | interaction | content`; `prop` requiere `codeProp`, `state` e `interaction` requieren `state`, y `content` requiere `part`. El eje no tiene por qué tener una sola clase: `State=Hover|Disabled` mezcla interacción y estado. `states` es una lista de `{ "name": "disabled", "control": "consumer" }` con `control: consumer | shared | internal`. `control` indica quién puede establecer el estado, no si hay que inventar una prop: `disabled` puede venir de HTML. Un estado `interaction` es interno; `shared` admite cambio desde el consumidor y desde la interacción del usuario. `default` puede representar el estado visual base, pero no justifica una prop pública. No fabriques una entrada de estado cuando no exista uno observado.

Para `kind: prop`, `codeProp` fija el nombre, no el valor de código. Durante la importación puedes proponer una correspondencia (por ejemplo `Size=Large -> size="lg"`) y escribir la implementación necesaria para verificarla: es una decisión de API candidata, no una medición de Figma ni un PASS. Comprueba la admisibilidad en el tipo y compara la configuración exacta renderizada con la variante Figma mediante `.agents/skills/validate-ds/SKILL.md`. Esa comparación puede confirmar empíricamente la correspondencia; el código que acabas de escribir, el parecido de los nombres o un comentario no la demuestran por sí solos.

Registra las correspondencias en la sección fija `## Figma to code correspondences` de `usage.md`, sin añadir codeValue a la ficha. Su única representación es un bloque JSON con `{ "schemaVersion": 1, "correspondences": [{ "caseId": "small-source", "status": "candidate" }] }`. Cada caso fidelity de metadata.verification necesita exactamente una entrada; caseId referencia allí las props, contenido, ref Figma, modos, estados y viewport, sin duplicarlos en usage. Los estados son candidate o confirmed por configuración, no por grupo de variantes. Sin correspondencia establecida, usa correspondences vacío y verification.unestablished con motivos; no se admite tabla manual ni None, sin retrocompatibilidad.

En la revisión, identifica la versión o snapshot de Figma y el commit de código cuando estén disponibles; para código aún sin commit, referencia la captura o artefacto examinado y las modificaciones locales relevantes. Si no puedes identificar la revisión, indícalo expresamente, no inventes un identificador ni uses solo la fecha como prueba de vigencia. `candidate` documenta lo que falta comparar; `confirmed` requiere refs de evidencia renderizada. Antes de reutilizar, contrasta esas revisiones y configuración con las actuales: si cambiaron o no puedes establecer su vigencia, conserva la evidencia histórica, trata la correspondencia actual como `candidate` en el informe y explica qué debe revisarse. Actualiza `usage.md` solo dentro de una importación/actualización autorizada del componente o por petición expresa de registrar el resultado; una consulta de mapeo o validación independiente devuelve la propuesta sin escribirla. El informe conserva el resultado de la ejecución actual; un PASS anterior no se hereda automáticamente.

El informe usa schemaVersion 4, kind rendered-comparison, result PASS, caseId, snapshotHash y configuration idéntica al caso fidelity, más metadataHash semántico de ese caso. comparison declara method agent-rendered-review o tool-rendered-comparison, reason y figmaRef exacta. figmaRevision/codeRevision tienen id real o id null con reason. files enumera path/SHA-256 de TSX, snapshot, CSS del mapa, CSS global y recursos relevantes; pueden añadirse dependencias examinadas. metadataAudit conserva el hash completo de la ficha como dato histórico, no gate de caducidad. artifacts exige una medida de navegador original y una captura PNG de Figma, tipadas y asociadas al caso. Añadir/quitar/modificar un caso asociado caduca la confirmación y exige recoger de nuevo; casos ajenos no lo hacen. Hashes/configuración/procedencia coherentes permiten auditar el registro, no autentican su origen ni demuestran fidelidad. El juicio de comparación sigue siendo explícito; un recibo NOT VERIFIED no se promociona automáticamente. Sin retrocompatibilidad para el informe anterior ni artefactos genéricos. Una ambigüedad de API sigue siendo DS_GAP.

Criterios para clasificar (orientativos: la decisión es tuya y se justifica con lo observado): lo que **ocurre** (hover, pressed) es una `interaction`, nunca una prop, porque el navegador ya lo hace; lo que se **declara** (selected, current) es un `state` que alguien fija; el **contenido** (`Icon=Mic`, `Icon=Camera`) es un hueco que se rellena (`content`), no una variante, y multiplicarlo en variantes es como un set llega a cientos; un **ajuste** (`Size=Large`) es una `prop`. Si varias filas casi idénticas (misma altura, icono, etiqueta y elemento final) parecen el mismo componente dibujado en distintos sitios, o un solo nombre cubre componentes distintos (un botón con texto, uno solo de icono y uno con una forma de onda), no lo resuelvas tú: indícalo en «No determinado» y pregunta al usuario si son el mismo componente. Nombra los booleanos como un adjetivo o estado (`disabled`, `loading`), nunca con `is*`, `has*` ni `show*`, y las props en camelCase.

Consulta `.agents/prop-vocabulary.json` antes de nombrar props: primero revisa lo heredado de HTML y de la librería usada. Registra cada prop declarada en el componente como un término con `concept`, `meaning`, `origin` (`authored | platform | library`) y `avoid` (sinónimos descartados); no predefinas escalas ni valores que Figma no mostró. Mantén `notBuilt` como lista de `{ "item": "...", "reason": "...", "evidence": "ref o hecho observado" }`. Incluye ahí decisiones como no exponer `hover` como prop, cuando apliquen; `[]` significa que no hubo exclusiones deliberadas. No copies el contenido de la propuesta de forma mecánica: justifica las decisiones con el preanálisis. Si tras consultar las fuentes una ambigüedad cambia la API (estado frente a prop, contenido frente a opción o dos ejes solapados), pide criterio antes de escribir esa parte; en los casos claros, muestra la propuesta y continúa sin esperar aprobación.

Antes del TSX, registra `parts` en `metadata.json`: cada clave es un nombre semántico estable en kebab-case; su `selector` es una única clase local de CSS Modules (por ejemplo `.root`), y `nodes` mapea cada clave de variante aplicable a un ref `<fileKey>:<nodeId>` observado. `root` es obligatorio y cubre todas las variantes; una parte condicional solo enumera las variantes en que existe. Si `figma.variants` está vacío, usa la clave de observación `default` en `parts[*].nodes` y en bindings/literales: `parts.root.nodes.default` apunta a la ref raíz del mapa. Esta clave no es una variante de Figma ni entra en `figmaCoverage.variants`. Marca el mismo elemento del TSX con su clase CSS y un atributo JSX de cadena literal `data-ds-part="<parte>"`; no uses una expresión como `data-ds-part={"root"}`, aunque su valor sea constante. No uses el nombre de la capa Figma como API automáticamente. No fabriques un nodo para una parte sin equivalente observado. El validador comprueba refs, marcadores y presencia de selectores, pero no demuestra todavía que la clase y el marcador estén en el mismo elemento; revisa eso en la comprobación visual.

Registra los estilos de texto, efecto o relleno aplicados que la herramienta permita identificar en `styles`. Un `styles: []` solo no distingue «no hay estilos» de «la herramienta no los devolvió», así que registra siempre `figmaCoverage.styles`: `{ "status": "captured", "source": "<llamada>" }` cuando la herramienta devolvió los estilos o confirmó que no hay, o `{ "status": "unavailable", "source": "<llamada intentada>", "reason": "<motivo>" }` cuando no los devolvió (entonces `styles` queda vacío y ningún registro usa `styleRef`). La plantilla arranca en `unavailable` con marcadores `<…>`: cámbialos por el motivo real o pasa a `captured` solo con evidencia. `verify-ds` rechaza en `metadata.json` cualquier valor que siga siendo un marcador completo `<…>`, un texto de relleno (`TODO`, `FIXME`, `TBD` o `XXX` al inicio, o el valor entero `pendiente`, `por definir`, `por rellenar`, `por completar`, `lorem ipsum…` o `...`) y una `figma.url` con marcadores. Aplica lo mismo a las líneas de `usage.md` y a un encabezado con `<Nombre>`, pero allí ignora comentarios HTML, bloques de código (``` o ~~~ o con sangría), fragmentos de código y las líneas que son una etiqueta HTML o JSX bien formada (`<br>`, `<details open>`, `<ExampleComponent variant="primary" />`): sus atributos llevan valor, salvo los booleanos de HTML (`open`, `disabled`, `hidden`, `checked`, `selected`, `readonly`, `required`, `controls`, `autoplay`, `loop`, `muted`). Por eso `<Una frase.>` o `<Cuando usarlo.>` se detectan aunque no lleven acento, y una línea suelta con un atributo booleano propio como `<Button primary />` también: muéstrala dentro de un bloque de código. Un marcador con forma de etiqueta (`<Nombre>` suelto, una sola palabra en minúsculas) no se detecta en el cuerpo de `usage.md`, solo en un encabezado. Admite `<` y `>` dentro de un texto (por ejemplo, una descripción que menciona `<button>`) y la palabra «Todo» en prosa. No puede juzgar si un motivo escrito es cierto. Un `unavailable` no es por sí solo `DS_GAP` si los valores esenciales sí están medidos. Cada entrada tiene un `ref` local único y estable (no derivado del nombre ni ID de Figma), `type: TEXT | EFFECT | PAINT`, `name`, `id`, `fileKey`, `key` solo si existe en una biblioteca, y `nodes` con al menos una aplicación `{ "node": "<fileKey>:<nodeId>" }`. Para texto por segmentos puede añadirse `{ "node": "...", "start": 0, "end": 5, "rangesSource": "getStyledTextSegments" }`. Guarda los índices tal como los entrega esa API, sin reinterpretarlos; quien consuma el rango debe usar su misma convención. Un rango documenta procedencia, no convierte la ficha en un modelo de texto enriquecido. `verify-ds` comprueba la forma, la coherencia de `figmaCoverage.styles` con `styles` y las refs, no si Figma devolvió todos los estilos o propiedades.

Cuando un binding o literal se asocia a un estilo, `styleRef` apunta a su `ref`, el `node` observado debe figurar entre sus aplicaciones y `styleOrigin` es `style`, `override` o `unknown`. La asociación al estilo **no demuestra** que esa propiedad proceda de él: usa `unknown` salvo evidencia específica de la propiedad. Para `style` u `override`, añade `styleOriginSource` con la llamada y el dato que lo justifican; una simple igualdad o diferencia de valores no basta, pues puede haber un override idéntico o modos distintos. Sin `styleRef`, no añadas campos de origen. El validador solo comprueba que la fuente esté declarada, no su veracidad.

Registra cada variable observada en `metadata.json.bindings` como `{ observation, part, variant, node, figmaProperty, cssSelector, cssProperty, variableId }`. `observation` identifica el binding bruto en el snapshot enlazado por `evidence`; `node` es el ref Figma exacto y debe coincidir con `parts[part].nodes[variant]`. `figmaProperty` identifica la propiedad inspeccionada (por ejemplo `fills[0]`), mientras que `cssSelector` y `cssProperty` son la traducción propuesta al código, no hechos medidos. Añade `modeOverride: { collectionId, modeName }` solo si ese nodo fuerza explícitamente un modo.

Para un binding directo a una variable de otra librería, añade en `externalVariables` una instantánea `{ id, cssName, type, value, source }`: `id` es el ID externo observado, `value` su valor resuelto en el modo base, `source` es una ref de nodo local que la usa y `cssName` se declara en `tokens.css`. No la registres como variable local. Si no puedes obtener el ID o el valor resuelto, `DS_GAP`; no inventes un token. El validador avisa de la instantánea, comprueba su valor base y el informe la identifica por ID; los cambios de modo externos todavía requieren revisión manual.

Si Figma no tiene binding para una propiedad implementada con un valor literal, registra `measuredLiterals` como `{ observation, part, variant, source, figmaProperty, cssSelector, cssProperty, value, translation }`: `observation` identifica la propiedad bruta en el mismo snapshot, `source` es el ref del nodo (no el nombre de la API), `value` es la traducción CSS y `translation` es `direct | approximate`. Para `approximate`, exige `figmaValue: { source: "PLUGIN", field, value }`: `field` y `value` coinciden exactamente con los de la observación, sin normalizar ni redondear. Si el valor bruto es un objeto con unidad, conserva ese objeto completo dentro de `value`; no traslades su unidad a otro campo. Por ejemplo, `lineHeight` conserva `{ unit: "PERCENT", value: 120.00000476837158 }` o `{ unit: "AUTO" }`. La herramienta concreta y la procedencia de la captura se registran en el snapshot; no sustituyen `figmaValue.source`. No renombres datos REST como PLUGIN: se necesita la observación del colector. Para `direct`, `figmaValue` es opcional. No registres un literal para una propiedad ligada a una variable en esa variante; `notApplicable` no es una lista de excepciones. Una propiedad no medida sigue siendo no determinada, nunca un literal plausible.

`AUTO` y otros valores cuya traducción a CSS no sea equivalente demostrada son `approximate`; por ejemplo, `line-height: normal` no se presume igual a `AUTO` de Figma. Para `PLUGIN.lineHeight` con `{ unit: "PERCENT", value: p }`, la expectativa independiente en píxeles es `fontSize × p / 100`, solo con el tamaño de fuente observado en Figma para el mismo nodo, variante y modos. Si la observación es `segments[n].lineHeight`, el tamaño debe corresponder al mismo segmento y rango. Si el tamaño es mixto o no está disponible, no apliques la fórmula. Con `{ unit: "PIXELS", value: n }`, el valor comparable es `n` píxeles; con `{ unit: "AUTO" }` no hay expectativa numérica independiente. Conserva el formato de [LineHeight de Plugin API](https://developers.figma.com/docs/plugins/api/LineHeight/). Para otros campos o contextos no comparables, busca una comparación visual contextual o deja `NOT RUN`. No redondees ni atribuyas intención a un número medido extraño en silencio: guarda el valor bruto, documenta la pregunta en `unresolved` con `blocking: false` cuando pueda implementarse y compárala renderizada. `verify-ds` contrasta el dato bruto con el snapshot, pero no demuestra la equivalencia visual ni calcula todas las traducciones CSS.

Si un nodo de texto mezcla segmentos con propiedades distintas, `figma.mixed` no es un valor escalar: no registres un único binding o literal para esa propiedad. Los rangos de `styles` solo indican dónde se observó cada estilo. Si la diferencia es esencial para implementar fielmente, informa `DS_GAP` antes de escribir; si no lo es, registra una duda no bloqueante en `unresolved` y marca esa parte `NOT VERIFIED` en el informe. `notBuilt` no vuelve conforme una propiedad esencial omitida. La ausencia de un ID de estilo no bloquea cuando los valores esenciales del nodo sí están disponibles.

El informe `node .agents/checks/verify-bindings.mjs` une ID de variable, `cssName` del inventario de tokens o de `externalVariables`, selector y declaración CSS. Solo evalúa selectores formados por clases y declaraciones directas. Recorre todas las declaraciones del CSS del componente: los literales directos sin medida de propiedades compatibles (incluida `font-family`) son FAIL; cualquier otra declaración sin observación, incluidos `var()` sin binding, shorthand, propiedades no soportadas, reglas condicionales y selectores complejos, es NOT_RUN con motivo. `calc()`, fallback de `var()`, herencia, modos forzados, redefiniciones locales del token y posibles conflictos con otras declaraciones del archivo tampoco se consideran PASS. Cada binding o literal registrado tiene `writtenStatus` para la identidad escrita y `status` para el alcance estático: un `status: NOT_RUN` por cascada no borra un `writtenStatus: PASS`. Un literal `approximate` con CSS escrito correctamente conserva `writtenStatus: PASS`, pero su `status` estático es `NOT_RUN` hasta la comprobación renderizada; una declaración CSS incorrecta sigue siendo FAIL. El informe estático no conoce la cascada de otros archivos ni el valor efectivo. Revisa cada hallazgo y corrige los problemas reales antes de cerrar el componente. No declares PASS por el mero hecho de que el informe no haya evaluado una propiedad. Para la conformidad final, sigue `.agents/skills/validate-ds/SKILL.md` y comprueba cada binding con `getComputedStyle` frente al valor Figma independiente del elemento; si no puedes hacerlo, informa NOT RUN y no declares Overall PASS. Las líneas `ADVISORY` avisan de un binding directo a una variable de una colección de primitivas: reflejas el binding de Figma y no cambian ningún estado. `verify-ds` rechaza además un binding cuyo tipo de variable no puede dirigir su `cssProperty` (por ejemplo, `COLOR` en `padding-left` o `FLOAT` en `background-color`); si falla, corrige el registro, no el CSS.

Si Figma liga una familia tipográfica que el navegador no tiene instalada, carga esa fuente en el proyecto antes de comparar capturas. Una variable CSS con el nombre correcto no evita que el navegador use una fuente de sustitución; no marques la tipografía como PASS sin comprobar la fuente renderizada.

## Recursos Y Casos Renderizados

Toda ficha incluye `verification: { schemaVersion: 1, geometryPolicy: "mapped-layout-v1", fonts: [], assets: [], stylesheets: [], inputs: [], cases: [], unestablished: [] }`. Define entradas reproducibles, no evidencia de confirmación ni sustituto de `usage.md`. `node .agents/checks/verify-render-plan.mjs .`, integrado en verify-ds, comprueba su conformidad; nunca declara fidelidad visual.

- `fonts`: una entrada por grupo idéntico de fontName: `{ id, css: { family, weight, style }, source }`. El ID font-SHA256 es determinista; familia/estilo medidos y todas las observaciones se derivan del snapshot, no se copian a la ficha. css declara descriptores exactos: weight como cadena con un único número de 1 a 1000, normal (400) o bold (700); style normal, italic u oblique. El peso solicitado no puede ser un rango, bolder/lighter, var() u otra expresión. Los rangos se admiten únicamente en el descriptor de la cara @font-face disponible y deben contener ese peso concreto. El plan y el registro lo validan antes de escribir. No deduzcas paquetes por familia ni cifras de peso por nombre de estilo sin comprobarlos. Un mismo grupo conserva referencias de nodo/segmento/variante sin repetir fuentes.
- `assets`: una entrada por paint IMAGE, incluido el oculto: `{ observation, index, imageHash, source }`. La observación apunta al array fills y el índice a su paint. El hash de imagen Figma no es el SHA-256 del archivo exportado. Sin hash capturado, no inventes un mapeo de asset.
- `source`: `{ kind: "file", path, sha256 }` para un archivo dentro del proyecto, incluido un archivo instalado de un paquete autorizado. Hash sobre sus bytes; no demuestra origen, licencia, equivalencia con Figma ni carga efectiva. Las fuentes se cargan por CSS y los assets por la API real. Si falta una fuente autorizada, `{ kind: "unresolved", reason }` y NOT VERIFIED; una carencia esencial sigue siendo DS_GAP antes de importar. Un asset es esencial cuando un caso puede renderizar su relleno `IMAGE`: dentro del caso, sin paint oculto ni opacidad 0, y sin ancestro oculto o con opacidad 0 de forma permanente (un caso de comportamiento solo lo revela mediante una propiedad `visible`). Un asset esencial `unresolved` o sin registrar bloquea `verify:imports` y la recogida de `finalize:import` igual que una fuente; no se inventa ni sustituye una imagen. No admite URLs temporales ni fuentes de sistema implícitas.
- `stylesheets`: rutas CSS globales exactas para la vista, incluidos tokens y cargas @font-face. El CSS Module importado por el TSX se carga desde el componente. La vista no hereda los imports de main.tsx o App.tsx.

verify-render-plan (incluido en verify-ds) y verification-preview comprueban que los tokens de metadata.tokens, bindings locales/externos y referencias var del prefijo DS tengan definiciones en CSS alcanzable por imports de ejecución del componente o verification.stylesheets, incluidos @import locales. Usa src/styles/tokens.css en stylesheets o un import real, o definiciones equivalentes alcanzables; no se impone un nombre de archivo. Un archivo listado solo en inputs, un CSS mapeado pero no importado o un import de tipos no cuenta como carga. Se comprueban también referencias de aliases CSS. Es un gate estático de disponibilidad de declaraciones, no demuestra que el selector/modo esté activo ni el valor efectivo: getComputedStyle y fidelidad siguen siendo obligatorios. CSS cargado por plugins, paquetes externos o código dinámico requiere un harness verificable; no se presume desde un listado de archivos.

La lista inicial de tipografía esencial exige cubrir observaciones TEXT de fontSize, fontWeight, lineHeight, letterSpacing, textAlignHorizontal y textAlignVertical, incluidos segmentos, mediante binding, literal, traducción enlazada con selector/propiedad CSS o delegación ya validada por identidad/configuración. Ocultar un nodo no lo excluye. Un mixed no autoriza un literal escalar: aplica el criterio de segmentos/DS_GAP. No cubre todas las propiedades visuales ni inventa datos ausentes del perfil.

Cada caso contiene los siguientes campos obligatorios:

```json
{
  "id": "small-source",
  "kind": "fidelity",
  "figmaRef": "FILE:1:3",
  "props": { "size": "small", "initial": "F" },
  "content": { "FILE:1:4": "F" },
  "modes": { "COL": "MODE_ID" },
  "viewport": { "width": 640, "height": 480 },
  "environment": { "attributes": { "data-theme": "dark" }, "classes": [] },
  "states": [],
  "expectations": []
}
```

El ID es único, con letras ASCII, números, guion o guion bajo. La ref pertenece a una variante capturada o a la raíz sin variantes. Props es JSON concreto admitido por la API, sin funciones ni elementos React. Content registra refs TEXT y textos exactos de esa configuración: fidelity coincide con los caracteres capturados. El check no demuestra que las props produzcan esos textos; contrástalos con el DOM. Modes fija el ID activo de cada colección capturada independientemente, también los destinos de aliases. Los modos de colecciones no usadas por el snapshot se revisan además por el flujo de tokens. Environment aplica atributos data-*, dir, lang y clases al ancestro de la instancia; revisa que active los scopes reales. Viewport usa píxeles CSS positivos hasta 16384 por eje, y se configura aparte en el navegador. States enumera `{ name, activation }`, instrucciones de la vía de control real, no prueba de ejecución ni hover sustituido por una prop.

Cada variante tiene al menos un caso fidelity o una entrada `unestablished: { figmaRef, reason }`, no ambas. La no establecida permanece NOT VERIFIED. No inventes valores ni un producto cartesiano: registra las configuraciones concretas que puedan examinarse, incluidos sus tratamientos visuales y modos aplicables.

Un caso behavior añade baseline (ID del caso fidelity), contenido alternativo permitido por la API y expectativas `{ kind: "intrinsic-size", observation, part, axis: "width" | "height" }`. Conserva ref, viewport, modos, entorno y estados de la base. Cada dimensión content no delegada necesita una expectativa y texto distinto para el nodo examinado. Es cobertura del plan, no prueba de comportamiento. Usa W/M para una inicial, envoltura solo si la API la permite; vacío y longitud máxima necesitan contrato explícito. No exijas que cambiar una letra cambie la altura ni infieras centrado del nodo de la alineación del texto. Estos casos no confirman variantes nuevas de Figma.

### Vista Y Transporte

#### Recogida Acotada Y Cierre

La vista muestra viewport esperado/obtenido en píxeles CSS antes de recoger. Una discrepancia no envía datos por defecto: ajusta el viewport y ejecuta `window.__dsVerification.collect()`. Solo para conservar un diagnóstico usa `collect({ diagnostic: true })`; su recibo tiene viewportMatches=false y no se puede publicar. La vista registra checkResult como retorno bruto de document.fonts.check, separado de faces: incluso una familia inexistente puede dar true. No se llama available ni afirma qué fuente renderizó los glifos. Por defecto no se carga configuración Vite del proyecto. Si hace falta, tras revisión/autorización humana usa `--config vite.config.ts --approve-config` después del puerto: carga explícitamente sus aliases/plugins y registra el hash. La opción es una guarda contra accidentes, no prueba de autorización; la configuración ejecuta código. No resuelve providers ni demuestra qué imports transitivos se ejecutaron.

`.agents/checks/lib/render-values.mjs` comparte conversiones independientes para fontSize, lineHeight/letterSpacing PIXELS o PERCENT con fontSize del mismo rango, y RGBA. AUTO/contextos desconocidos permanecen no comparables. La vista expone expectativas sin asignar PASS ni resolver bindings: todavía se necesitan tokens/modos y normalización independiente en el navegador. Si fontSize está ligado a una variable, no usa el escalar capturado como expectativa para otros modos.
