# Design System rules

Apply when reading, editing or generating `src/` or `design-system/` files.

Inspect color:PART:PROPERTY checks against raw snapshot solid paints and active alias modes, not only geometry or the CSS token spelling. Computed-color PASS is not evidence of visible paint, a loaded mask or correct composition. Unsupported color mappings need specific fidelity reviews; behavior must PASS. Consume the generated report in verify:imports/finalize:import instead of inventing delivery counts, mode coverage or approvals from warnings. Diagnostic reports do not revalidate persisted confirmations.

Every imported component requires metadata.verification with font/image sources and reproducible fidelity/behavior cases. Run `node .agents/checks/verify-render-plan.mjs .` before rendering (included in verify-ds). A valid plan or transferred measurement never establishes visual PASS; follow validate-ds for independent state/mode/font/content comparison.

Configured native checked/disabled states may use an explicit states[].verification assertion with a unique own-control selector and boolean value. Compare original nativeStates readings, never infer state from props, ARIA or classes or remove declared states to enable collection. Native FAIL/NOT RUN blocks confirmation; unsupported activation needs an explicit environment-browser harness. These assertions do not execute interaction sequences or replace keyboard/focus checks.

Missing essential resources stop a new import before implementation; report DS_GAP/BLOCKED and ask for authorized sources, or stop without writing if no interaction is available. After permitted implementation or visual edits, run `npm run finalize:import -- ROOT METADATA --diagnose` for each changed component and inspect every measured part/case before presenting results. Correct demonstrated defects and repeat; unavailable execution is NOT RUN/BLOCKED. This temporary-only mode can inspect existing incomplete code without publishing or confirming, but never authorizes bypassing an import block. Missing resources remain blockers and may affect geometric deltas; do not infer their cause automatically. Delivery still requires --collect, explicit rendered reviews and verify:imports.

Before declaring an import complete, use the integrated `npm run finalize:import -- ROOT METADATA --check` gate over current persisted confirmations, or verification-plan.mjs close for the individual component with published evidence for every fidelity and mandatory behavior case followed by the repository gate. Require current confirmed cases; measured, pending, stale or failed obligations are not a completed visual import. The checks are read-only, not a replacement for static/manual checks or independent visual judgment. Only explicitly authorized --collect/--reviews modes publish measurements or record supplied reviews. Bound browser collection and external waiting separately; a viewport diagnostic is not fidelity evidence.

The 1px TEXT geometry threshold is provisional, not cross-font/renderer calibration. Even a numeric PASS needs a specific rendered checkReviews entry for geometry:PART with retained case artifacts before measured/confirmed. It never overrides FAIL/NOT RUN. General visual approval alone is insufficient.

Account for every source node in fidelity cases, including containers. verification.nodeCoverage rules must be demonstrable; unresolved is pending, not coverage. Literal CSS syntax results must match the declarations derived for the component; token substitution/dynamic styles still require their separate checks. Diagnose generated App.tsx at application scope as well. Optional headless collection publishes evidence and requires appropriate write authorization; it never fabricates interaction paths, tolerance overrides or visual judgments.

Require capture v2, verification.geometryPolicy=mapped-layout-v1, browser measurements v2 and confirmation reports v4. Geometry/font checks are generic, not component-specific. A numeric FAIL, missing essential font or unresolved essential image blocks confirmed; noncomparable fidelity requirements need individual rendered reviews. All behavior cases linked by baseline are mandatory: retain their published measurements and require every behavior check PASS; no manual review rescues missing, failed or noncomparable behavior. Noncomparable/unexecuted obligations mean pending verification, not a demonstrated design defect. Preserve original matching measurementVersion in browser bodies/receipts; old producer rules stale confirmation and require recollection, while internal version mismatches remain invalid. Always report static conformance separately from visual coverage and pending/unestablished cases.

For imported components, run `node .agents/checks/verify-figma-evidence.mjs .` against the persisted import snapshot before rendered validation. Every map entry requires evidence, without exceptions. Capture gaps, manual decisions and composite translations need review. Static evidence coverage does not prove visual fidelity or complete file-level token extraction.

- Before adding a UI component, search `design-system/inventory.json`, `design-system/components/` and `src/components/`; reuse an existing match.
- Keep comparator rule versions distinct from explanatory prose. Rule changes make confirmations stale; numeric inconsistencies remain errors. A partial vector-position PASS is not a shape PASS. Behavior invariants are explicit and measured separately from fidelity.
- Resolve Figma components through `design-system/relationships/figma-code-map.json`. Check `figma-state.json` for nested dependencies.
- Reuse a mapped nested component from `src/components/`; do not redraw it. Report new variants before implementing them.
- Use Design System tokens for observed Figma variable bindings. Where Figma has no variable binding, use only an observed literal recorded in the component's `measuredLiterals`, preserving any approximate-translation verification requirement. Do not invent color, spacing or typography values or replace a bound token with a literal.
- Read and follow `.agents/rules/design-system-composition.md` and `.agents/rules/design-system-accessibility.md`.
- Consult `.agents/prop-vocabulary.json` when naming props. Name boolean props as a bare adjective or state (`disabled`, `loading`), never `is*`, `has*` or `show*`, and write props in camelCase.
- Do not invent a substitute for an unmapped element. Report `DS_GAP` and explain what is missing.
- Do not rebuild a Figma vector (VECTOR, BOOLEAN_OPERATION, STAR, POLYGON, LINE) with CSS shapes. Reproduce it from its original export (`figma-vectors.mjs`, listed by `requirements` as `vectors`); a CSS approximation is a decision that needs the user's approval and a rendered visual review, because geometry checks cannot see its color, stroke or shape.
  This is an agent obligation, not an automated check: the current gates do not link an exported SVG to the implementation or verify that it is used.
- Record only implemented components and screens in `design-system/inventory.json`.
- Never edit `src/styles/tokens.css` by hand; regenerate it with `node .agents/skills/create-ds-from-figma/scripts/generate-tokens-css.mjs .` after changing token JSON, `figma-state.json` or `externalVariables`.
- Install the dependencies in `package.json` before running Node checks if they are missing: `verify-ds.mjs` and `verify-bindings.mjs` require PostCSS and postcss-selector-parser; `verify-ds.mjs` and `verify-props.mjs` require TypeScript.
- Before finishing UI work, run `node .agents/checks/verify-ds.mjs`, `node .agents/checks/verify-props.mjs` and `node .agents/checks/verify-bindings.mjs` from the repo root. Complete the manual `.md` checks in `.agents/checks/` and follow `.agents/skills/validate-ds/SKILL.md` for rendered values. `.agents/checks/tests/` contains kit tests and `.agents/checks/lib/` contains shared code; neither is a check to run for each UI task. Report checks not run and why.
- Before delivering an import, run `npm run verify:imports` locally. It revalidates persisted confirmations for every inventoried component, including required behavior and essential resources; candidates, stale records and missing cases fail delivery. It independently diagnoses application literals in the locked kit Chromium without executing application code. Missing browser execution is NOT RUN, not success. It never remeasures component geometry or promotes a candidate automatically. No CI or Git hooks are configured; do not claim that commits or pushes are automatically blocked.
