# CREATE DS FROM FIGMA

Proyecto para arrancar un Design System desde 0 dentro de este repo preparado.

No trae tokens, componentes ni pantallas. El agente analiza la URL de Figma antes de escribir y crea el DS cuando el componente puede importarse.

## Usar

Instala las dependencias con `npm install`. Antes de importar, necesitas acceso a Figma y un transporte capaz de ejecutar el colector en Plugin API y guardar su respuesta sin transcripción del modelo. Una conexión que solo devuelve contexto de diseño no basta.

- Si tu entorno dispone del orquestador de Codex requerido por el adaptador, el agente puede usarlo con la conexión de Figma disponible.
- En Claude Code u otro entorno sin ese adaptador, comprueba primero si existe una conexión MCP directa compatible (stdio o HTTP) y autorizada. Si existe, usa su configuración y el mecanismo de autenticación que requiera; no presupongas que hacen falta un servidor nuevo o credenciales nuevas. Si no existe, solicita la configuración de una conexión compatible. No se reutiliza automáticamente el OAuth del editor.

Antes de ejecutar una conexión directa, el usuario debe revisar y autorizar su configuración. --approve-connection evita una ejecución accidental, pero el agente puede añadir la opción: no acredita revisión humana ni sustituye los permisos del entorno.

Consulta [la configuración y comprobación del transporte](.agents/skills/create-ds-from-figma/references/figma-evidence.md). No hay una conexión de Claude Code validada en este repo. Esa falta de validación no implica que todas sus conexiones sean incompatibles: hay que comprobar la conexión concreta. Si no existe transporte operativo, informa `NOT RUN` y `DS_GAP` sin crear el componente ni copiar respuestas a mano; es un bloqueo de la importación en ese entorno, no del mantenimiento del kit.

Abre este repo en tu IDE, abre un chat con la IA y pide:

```text
Crea un DS

<URL de UN componente de Figma>
```

El componente debe disponer de variables locales en su file de origen o de bindings a variables externas con ID y valor resuelto verificables. La URL puede apuntar a un componente, un component set, una variante o una instancia cuyo componente principal se pueda resolver; un frame o pantalla no se importa por este flujo.

Antes de crear archivos, el agente identifica el componente y sus variantes, lee **todas** las colecciones del file de origen y resuelve los componentes anidados. Si falta uno local, informa `DS_GAP` y espera su URL sin escribir archivos. Solo prepara el scaffold y los tokens pese a ese bloqueo si el usuario lo pide expresamente; el componente bloqueado nunca figura como importado. Si el análisis permite continuar, vuelca un JSON por colección e implementa **solo** el componente pedido.

Si se prepara solo el scaffold, `App.tsx` queda válida y vacía hasta importar el primer componente.

Siguiente componente: otra URL. Pantalla: cuando ya haya componentes importados.

`npm run verify:imports` es el gate local de entrega de los componentes reales del repositorio (opcionalmente `npm run verify:imports -- ROOT`). Reutiliza la API de `verify-ds`: cruza inventario, mapa y fichas, y exige al menos un caso de fidelidad por componente, todos confirmados y vigentes, sin correspondencias pendientes, fallidas o no establecidas. Revalida informes, hashes, recursos esenciales y comportamiento obligatorio desde los artefactos persistidos; no vuelve a medir geometría ni confirma por sí mismo la fidelidad visual. Cualquier incumplimiento devuelve código distinto de cero. Los avisos informativos no se convierten en errores indiscriminadamente.

El gate comprueba además los literales CSS de la aplicación con el Chromium fijado del kit, en una página en blanco: no ejecuta App.tsx, configuración Vite ni código del proyecto. Este diagnóstico es independiente del preflight del componente y se conserva aunque falle el DS; si falta el navegador, muestra NOT RUN y falla la entrega. Su alcance es el soporte de literales aplicables en ese Chromium, no la cascada, tokens sustituidos, comportamiento React o fidelidad visual. No escribe archivos del proyecto ni necesita un manifiesto temporal.

El diagnóstico se exige si existe index.html en la raíz o una entrada App/app/main/index en src con extensión JS/TS, JSX/TSX o sus formas de módulo. Incluye los literales de todos los archivos JS/TS y CSS de src, aunque la demo se llame Showcase o use otro nombre desde index.html. Devuelve los indicadores detectados en application.signals; sin ellos indica NOT APPLICABLE con el alcance explícito, sin inferir que cualquier archivo de una biblioteca sea una aplicación. Un index.html aislado no permite aprobar un kit vacío. Los errores estructurales incluyen structure.reason además de errors.

Un kit sin DS ni aplicación pasa con NOT APPLICABLE; un scaffold coherente sin componentes también puede pasar y diagnostica la demo si existe. Un scaffold parcial falla. No se acepta un componente sin resumen o sin casos. Ejecuta el gate localmente antes de entregar una importación, además de las pruebas del kit cuando correspondan. Sus códigos de salida no bloquean commits ni pushes por sí solos: no hay pipeline remoto, protección de rama ni hooks configurados por el kit.

La ruta integrada es `npm run finalize:import -- ROOT METADATA --collect`: recoge/publica mediciones con el runtime fijado y ejecuta el gate, sin fabricar una revisión visual. Por defecto solicita un puerto libre automático; `--collect --port 5189` fija uno explícito y falla si está ocupado, sin conectarse a un servidor ajeno. El resultado muestra el puerto y las URL efectivos en collection.preview y los conserva en result.json; la vista se cierra al terminar la recogida. Manifiesto y resultado quedan temporales; las mediciones originales sí se publican en el proyecto. Si faltan fuentes o imágenes esenciales, enumera familia, estilo y peso registrado (o el paint de la imagen) y pide un origen autorizado antes de recoger; `verify:imports` también las bloquea. El adaptador de bajo nivel sigue permitiendo mediciones diagnósticas sin esos recursos.

Tras comparar realmente los artefactos, ejecuta `npm run finalize:import -- ROOT METADATA --reviews REVIEW_FILE`. Un archivo presente pero inválido (`null`, `false`, `0`, `""` u otro valor que no cumpla el contrato) falla aunque las confirmaciones anteriores ya pasen el gate; solo omitir `--reviews` equivale a no registrar nada. El archivo contiene `schemaVersion: 1` y `cases: [{caseId, review}]`, con una revisión explícita por caso fidelity y el contrato existente del comando report (juicio, revisiones, artefactos publicados, checkReviews y comportamiento). Deriva/persiste informes y hashes en `design-system/verification/`, revalida y reemplaza atómicamente solo el JSON de correspondencias de usage.md, conservando Use/Do not y metadata. No admite aplicar revisiones mientras vuelve a recoger: deben referirse a los artefactos retenidos que se revisaron. Una revisión inválida se rechaza antes de persistir informes; si falla una comprobación posterior pueden conservarse informes válidos inmutables sin enlazar, nunca una confirmación inválida escrita en usage.md.

La ficha no puede incluir sus propios archivos de salida como entradas examinadas de la confirmación. Antes de persistir informes, la finalización rechaza también usage.md si llega por inputs adicionales del revisor o por dependencias examinadas del componente/comportamiento: escribirlo caducaría la confirmación inmediatamente. El umbral AABB_SIZE_DIAGNOSTIC_THRESHOLD de tamaño es independiente de las tolerancias de posición y fidelidad; solo filtra diferencias informativas superiores a 1 px, no establece una tolerancia de forma ni una calibración visual.

`npm run finalize:import -- ROOT METADATA --check` comprueba sin escribir. Los tres modos ejecutan el gate de todo el repositorio: una revisión del componente no oculta errores de la demo ni de otros componentes. No genera el juicio visual del revisor. El cierre conserva avisos estáticos de bordes parciales y diagnósticos de diferencias de tamaño AABB, también visibles en compare. Estos últimos no convierten una geometría no comparable en un FAIL objetivo ni certifican la forma.

### Recursos Antes De Implementar

Tras capturar y antes de escribir el componente, ejecuta `node .agents/skills/create-ds-from-figma/scripts/verification-plan.mjs requirements SNAPSHOT`. Conserva los requisitos originales y añade `resources` con fuentes agrupadas e imágenes agrupadas por `imageHash`, nodos y variantes afectados. Son candidatos observados, no carencias esenciales: casos y descriptores CSS quedan pendientes, sin deducir pesos del nombre de la fuente. El snapshot temporal del preanálisis puede estar fuera del proyecto. Pide en un solo mensaje los orígenes autorizados necesarios para la implementación prevista; no instales paquetes ni sustituyas imágenes por su nombre.

Con una ficha en preparación, `node .agents/skills/create-ds-from-figma/scripts/verification-resources.mjs inspect ROOT METADATA` comprueba registros y hashes sin escribir ni necesitar TSX o navegador. Para registrar un archivo existente autorizado:

```sh
node .agents/skills/create-ds-from-figma/scripts/verification-resources.mjs register ROOT METADATA font FONT_ID SOURCE_PATH
node .agents/skills/create-ds-from-figma/scripts/verification-resources.mjs register ROOT METADATA image IMAGE_HASH SOURCE_PATH
```

`SOURCE_PATH` es relativo al proyecto. El comando calcula SHA-256 y solo modifica campos `source` existentes: una fuente por ID o todas las apariciones capturadas de la imagen en esa ficha. Identidades desconocidas, entradas ausentes/duplicadas, rutas externas y conflictos fallan sin modificarla. Cambiar una ruta o hash ya registrados exige `--replace` explícito; repetir el mismo registro no reescribe. No crea CSS, no edita `stylesheets`, no instala/copia recursos ni confirma su licencia, identidad o peso. Separa `registration: REGISTERED`, `configuration: DECLARED` o `NOT VERIFIED`, y `loading: NOT RUN`: registrar no es cargar ni confirmar. Cambiar recursos puede caducar evidencias anteriores.

La comprobación estática busca `@font-face` en `verification.stylesheets`, sus imports CSS incondicionales y los imports/reexports estáticos alcanzables desde el componente. Resuelve CSS de paquetes instalados (incluidos subpaths exportados) sin ejecutar JavaScript; no sigue efectos secundarios de paquetes JS, imports dinámicos/globs ni condiciones CSS. Cualquier import con `?` queda sin acreditar, también dentro de `@import`: incluye worker/sharedworker, raw/url/inline, parámetros de caché y consultas desconocidas. Compara la ruta real del archivo registrado, familia, estilo y peso (incluidos rangos). `DECLARED` acredita un enlace declarado, no que el navegador seleccione ese archivo, lo cargue o use sus glifos. Formas no resolubles o no soportadas requieren revisión, sin generar un FAIL visual falso; `configurationWarnings` y `REVIEW_FONT_CONFIGURATION` conservan el diagnóstico. El gate lo muestra en `fontConfiguration`. Las fuentes esenciales sin registro o sin cara cargada siguen bloqueando; el adaptador de bajo nivel puede recoger diagnósticos, nunca confirmar por esos avisos. La ampliación del analizador compartido incrementa la versión del comparador: las confirmaciones anteriores caducan, no se relabelan ni se corrompen.

La resolución de `exports` usa [resolve.exports](https://github.com/lukeed/resolve.exports), fijado como dependencia directa, no Node require ni una copia interna de Vite. Preserva el orden de condiciones, claves exactas, comodines y exclusiones. Es un diagnóstico conservador, no un resolvedor completo de bundler: con `import` activo exige el mismo destino CSS bajo las combinaciones de browser/module y los modos no fijados, development y production; para `@import` considera también style activado/desactivado. Si un resultado cambia, no existe, ofrece varias alternativas o requiere condiciones desconocidas, queda NOT VERIFIED. Tampoco interpreta browser remapping ni ejecuta configuración del proyecto. Los subpaths antiguos sin exports pueden apuntar a un CSS explícito; una raíz exige un destino único de style/main. Ninguna exclusión de exports permite recurrir al archivo físico. Los destinos y symlinks deben permanecer dentro del proyecto. Esta política no demuestra equivalencia con aliases/plugins arbitrarios del proyecto ni la carga del recurso.

El peso solicitado en `verification.fonts[].css.weight` es una cadena con un único número de 1 a 1000, `normal` o `bold`; no admite rangos, valores relativos ni variables. Los rangos pertenecen al descriptor de la cara disponible en `@font-face`, que puede satisfacer ese peso concreto. El plan y el registro rechazan pesos ambiguos antes de escribir. Gate y finalización comparten deduplicación de `nextActions`: `targets` contiene las rutas de las fichas destinatarias y se unen al agrupar acciones idénticas; comandos o recursos diferentes no se colapsan. Las acciones globales pueden no tener targets. Los avisos de fuentes se conservan en su detalle y también en `warnings` del gate, prefijados por componente, sin elevarlos a errores.

`npm run test:resources:mutations` ejecuta mutaciones dirigidas en una copia temporal, sin alterar el checkout. Primero exige que pasen las pruebas sin mutar y después comprueba que estas rechacen cambios de hash, cobertura, sustitución, alcance de escritura, acciones y enlaces de fuentes. Guarda el resumen en `test-results/resource-mutations.json` (ignorado por Git) y falla ante supervivientes o errores de infraestructura. Es una selección explícita, no una puntuación de cobertura exhaustiva ni una prueba contra Figma real; no sustituye `npm test`.

El diagnóstico, `verify:imports` y `finalize:import` comparten `nextActions` estructurado: códigos estables, recursos/casos, prerrequisitos, permisos y comando como ejecutable más argumentos, con entradas pendientes tipadas. No son cadenas de shell ni autorizaciones; completa los argumentos con rutas aprobadas y respeta los permisos del entorno. Sin `imageHash` legible se pide revisar la captura, no inventar una identidad. Un registro inválido requiere revisar sus bytes, nunca añadir `--replace` automáticamente. El gate conserva sus errores estructurales aunque todavía no pueda derivar acciones de recursos.

Las regresiones reproducibles usan fixtures sintéticos versionados: comprueban que una geometría defectuosa, correspondencias candidatas o literales inválidos en la demo impiden la entrega. No dependen de ramas locales de prueba ni demuestran fidelidad contra Figma real.

Cada componente mapeado exige una captura estructurada e inmutable de Figma, separada de las decisiones de API y CSS, sin excepciones. El colector preserva valores brutos, modos, estilos y limitaciones; el SHA-256 identifica la captura, no la revisión de Figma. El kit sigue vacío: las capturas nacen al importar, en `design-system/figma/snapshots/`.

`node .agents/checks/verify-figma-evidence.mjs .` comprueba cobertura y fidelidad contra la captura de importación. verify-ds incluye errores y avisos, y rechaza fichas sin evidencia. Valida referencias y reglas, no equivalencia visual ni calidad de razones manuales. El CLI portable captura directamente mediante MCP por stdio o HTTP, sin APIs del editor ni copia del modelo; requiere conexión y autenticación configuradas. Codex dispone además de un adaptador opcional. Procedimiento y límites en [.agents/skills/create-ds-from-figma/references/figma-evidence.md](.agents/skills/create-ds-from-figma/references/figma-evidence.md).

`node .agents/skills/create-ds-from-figma/scripts/figma-capture.mjs propose SNAPSHOT` ofrece candidatos conservadores de clasificación; no decide la API. `node .agents/skills/create-ds-from-figma/scripts/figma-capture.mjs compare ANTES DESPUES` compara una relectura opcional después de comprobar la importación original, sin modificar componentes.

`node .agents/skills/create-ds-from-figma/scripts/figma-capture.mjs dimensions SNAPSHOT` devuelve la semántica de dimensiones TEXT con refs de apoyo. Toda ficha exige `evidence.textDimensions`: ancho/alto fijo, dependiente del contenido o no determinado, separado de su tratamiento de implementación. No permite congelar una dimensión intrínseca al tamaño del texto de ejemplo. El check verifica cobertura y enlaces, no comportamiento CSS: la comparación renderizada sigue siendo necesaria. No cambia el perfil de captura ni añade retrocompatibilidad a las fichas.

`src/styles/tokens.css` no se edita: lo genera `.agents/skills/create-ds-from-figma/scripts/generate-tokens-css.mjs` y `verify-ds` comprueba que coincide. En un DS generado, instala las dependencias y ejecuta `node .agents/checks/verify-ds.mjs`, `node .agents/checks/verify-props.mjs` y `node .agents/checks/verify-bindings.mjs`. Los dos primeros validan la coherencia del DS y la API de componentes; el último informa cobertura y diferencias de bindings CSS sin bloquear por sus hallazgos.

## Verificación Reproducible

### Inventario Sin Transcripción

El snapshot solo guarda valores de variables usadas y sus alias. `figma-inventory.mjs` captura por separado todas las colecciones y variables locales, modos y valores, y las dependencias remotas de alias. No cambia metadata, relaciones ni el perfil del snapshot.

```sh
node .agents/skills/create-ds-from-figma/scripts/figma-inventory.mjs capture FILE_KEY CONFIG --approve-connection
node .agents/skills/create-ds-from-figma/scripts/figma-inventory.mjs save SESSION INVENTORY
node .agents/skills/create-ds-from-figma/scripts/figma-preanalysis.mjs . --inventory INVENTORY --snapshot SNAPSHOT
node .agents/skills/create-ds-from-figma/scripts/generate-token-json.mjs plan . --inventory INVENTORY
node .agents/skills/create-ds-from-figma/scripts/generate-token-json.mjs save . --inventory INVENTORY
node .agents/skills/create-ds-from-figma/scripts/generate-token-json.mjs check . --inventory INVENTORY
node .agents/skills/create-ds-from-figma/scripts/generate-tokens-css.mjs . --inventory INVENTORY
```

CONFIG usa la misma conexión MCP autorizada: no descubre credenciales ni reutiliza OAuth automáticamente. `bridge FILE_KEY` genera el adaptador opcional Codex. capture solo escribe una sesión temporal; save es explícito y nunca sobrescribe otro inventario. El hash canónico ordena conjuntos por ID y conserva el orden de modos. Verifica integridad, tipos y referencias, no autenticidad, vigencia ni revisión atómica. capturedAt fecha el sellado, no una revisión de Figma. Cada bloque relee y rechaza diferencias por checksum.

plan/check/preanalysis son de solo lectura. save de tokens valida y mezcla JSON/estado usando el preflight; conserva nombres publicados, ámbitos, serializaciones y registros antiguos ausentes de la captura. Nuevos ámbitos quedan null y FLOAT no recibe unidad por defecto. Los alias entre colecciones solo se derivan si su valor es independiente del modo; los demás bloquean y requieren resolución explícita. Revertir fallos ordinarios de escritura no equivale a una transacción resistente a una caída del proceso. No prepara React ni instala recursos.

`--inventory` es explícito, nunca se descubre por proximidad. check y el generador CSS comparan hechos observados y enumeran registros conservados; conservar no demuestra presencia actual en Figma. Sin el argumento no afirman trazabilidad. No hay enlace persistente nuevo en metadata ni estado. `figma-capture.mjs nested SNAPSHOT MAP` distingue mapped/external/missing/unresolved usando identidad estable; missing exige procedencia local probada.

Exportación opcional: `node .agents/skills/create-ds-from-figma/scripts/figma-reference.mjs capture FILE_KEY NODE_ID SCALE CONFIG --approve-connection`, o `bridge FILE_KEY NODE_ID SCALE`. `save ROOT SESSION` publica el PNG original en design-system/verification/artifacts y devuelve un figma-screenshot tipado para report. Escala explícita mayor que cero y como máximo cuatro, límites de 32 MiB/16 megapíxeles, CRC y hash. report comprueba dimensiones y asocia caso/snapshot; exportar no confirma fidelidad. La captura fragmentada aborta si cambia el PNG.

### Vectores Originales

La exportación original o la aproximación aprobada es una obligación del agente: los checks actuales no vinculan el SVG exportado con el código ni detectan por sí solos una reconstrucción CSS. No se presenta como una garantía automática de fidelidad.

Un nodo vectorial de Figma no se reconstruye con cuadrados rotados y bordes CSS: su forma, su trazo y su color se pierden sin que ninguna comprobación de geometría lo vea. `verification-plan.mjs requirements SNAPSHOT` lista como `vectors` los nodos VECTOR, BOOLEAN_OPERATION, STAR, POLYGON y LINE observados (candidatos sin clasificar, no recursos que haya que autorizar) y propone `EXPORT_VECTOR_SOURCES`.

```sh
node .agents/skills/create-ds-from-figma/scripts/figma-vectors.mjs capture FILE_KEY NODE_ID CONFIG --approve-connection
node .agents/skills/create-ds-from-figma/scripts/figma-vectors.mjs save SESSION EXPORT.json
node .agents/skills/create-ds-from-figma/scripts/figma-vectors.mjs svg EXPORT.json VECTOR_ID RUTA.svg
```

`capture` usa la misma conexión MCP autorizada que el resto (también existe `bridge FILE_KEY NODE_ID` para el adaptador de Codex) y transfiere el SVG exacto de `exportAsync` por bloques comprobados, sin transcripción. El sobre sellado guarda el SVG, las cajas de maquetación (`bounds`) y de renderizado (`renderBounds`): el SVG exportado se recorta a lo que el nodo dibuja, así que `renderBounds` es lo que lo coloca respecto a la raíz, no `bounds`. `svg` escribe el archivo tal cual y nunca sobrescribe. El SVG se analiza con un parser XML estricto (`saxes`): se rechaza lo mal formado o incompleto, un DOCTYPE, entidades, CDATA o instrucciones de proceso, un elemento fuera del espacio de nombres SVG y los elementos que ejecutan, cargan o estilan contenido (`script`, `style`, `foreignObject`, `iframe`, `a`, animaciones...). Los valores de atributo se restringen por gramática y no por búsqueda de palabras: no pueden llevar barras invertidas, comentarios ni `@` (así los escapes CSS como `u\72l(` o `@im\70 ort` no tienen dónde esconderse), solo pueden usar las funciones que escribe el exportador (`url`, `rgb`, `rgba`, `hsl`, `hsla`, `matrix`, `translate`, `rotate`, `scale`, `skewX`, `skewY`; `image-set()` y similares se rechazan), `url()`, `href`, `xlink:href` y `src` solo pueden apuntar a un fragmento local `#id` o a una imagen raster `data:` en línea, `style` se limita a las propiedades que emite Figma, y de los atributos con espacio de nombres solo se admiten `xlink:href`, `xml:space` y `xml:lang` (`xml:base` redirigiría las referencias). También se acotan elementos y profundidad. No es un sanitizador: rechaza lo que el exportador de Figma nunca emite, de modo que lo que pasa es inerte como `<img>` o archivo y no contiene contenido activo ni externo en lo que se comprueba, pero insertarlo en línea en la página exige revisarlo o reconstruirlo desde un DOM filtrado. Es el SVG original, no una autorización ni una equivalencia CSS ni una prueba de fidelidad renderizada: usarlo como archivo del proyecto requiere la misma aprobación que cualquier recurso, y aproximar la forma con CSS es una decisión explícita que debe revisarse con la comparación visual. ### Cierre De La Importación

El flujo se detiene antes de implementar si faltan fuentes o imágenes esenciales autorizadas. Pregunta por ellas juntas; si el agente no puede interactuar, debe devolver BLOCKED sin escribir código ni registrar el componente. Para obtener feedback sobre código existente antes de publicar evidencia:

```sh
npm run finalize:import -- . design-system/components/Nombre/metadata.json --diagnose
```

Este paso forma parte del bucle de implementación: medir, revisar diferencias, corregir defectos demostrados y volver a medir antes de presentar el resultado.
